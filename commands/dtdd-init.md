# /dtdd-init — scaffold DTDD into this repo

Set up the current repository to follow the DTDD methodology. **Every step below is
idempotent and non-destructive: if a file already exists, skip it (or merge additively where
the file is meant to grow — the logs, CLAUDE.md). Never overwrite or clobber an existing doc,
log, or CLAUDE.md.** Report at the end exactly what was created, what was skipped as
already-present, and what was proposed.

## 1. Doc skeletons — both Fact tiers

- Copy `${CLAUDE_PLUGIN_ROOT}/templates/DESIGN.template.md` to `docs/templates/DESIGN.template.md`
  (skip if present). This is the fixed 12-section template every component `DESIGN.md`
  follows.
- Create `docs/architecture/architecture.md` as a stub (skip if the repo already has an
  architecture doc — look for `docs/architecture/*.md` before creating): a title, a one-line
  purpose ("the Repo Fact: cross-component truth — system shape, component inventory, shared
  flows"), and empty sections for *Components*, *How They Connect*, and *Open Questions*.
- Create `docs/architecture/data-model.md` as a stub (same skip rule): purpose line ("the
  shared data model — schemas and storage shapes no single component owns") and an empty
  *Entities* section.

Do not generate per-component `DESIGN.md` files — those are written by whoever does the
reasoning about each component (the DTDD worker on its first change to that component, or a
human), never bulk-generated by a scaffolder.

Also ensure the target's `.gitignore` covers `tmp/` — DTDD runs write throwaway specs and
plans under `tmp/<run_id>/`, and those must never be staged. Append the line if missing;
never rewrite an existing `.gitignore`.

## 2. The two logs

- Copy `${CLAUDE_PLUGIN_ROOT}/templates/decisions-log.md` to `docs/decisions/decisions-log.md`
  (skip if present).
- Copy `${CLAUDE_PLUGIN_ROOT}/templates/improvements-log.md` to `docs/improvements/improvements-log.md`
  (skip if present).

## 3. CLAUDE.md methodology rules block

Compose a DTDD rules block containing, generically and briefly:

- **Reading priority:** design docs first (component `DESIGN.md` → repo architecture docs →
  other docs), code only to verify the docs; a doc↔code discrepancy is flagged and resolved
  in the docs deliberately, never silently patched in code.
- **Present-state discipline:** every doc except the two logs describes the current state —
  no changelog verbs, no dates; history lives only in the logs; permanent docs never cite
  transient log entries as their explanation.
- **Shared-code consumption:** shared code is consumed through its public, published
  surface — in ecosystems with built packages (a JS/TS workspace), by package name, never
  via deep relative-source imports into another package's internals; in other ecosystems,
  through the module boundary the language provides. A public-surface import survives
  publishing and refactoring; a reach into internals silently diverges. State this rule in
  the target ecosystem's own terms, and omit it where no such seam exists.
- **Document Ownership:** component code/tests/`DESIGN.md` belong to the worker changing that
  component; shared docs (architecture, data model, logs, root README) belong to the
  orchestrator at fan-in; templates and CLAUDE.md itself change only with explicit human
  approval.
- **Review gates:** before any commit, the design-sync agent runs in an independent context
  (never inline in the authoring session) and creates the single-use commit stamp; the commit
  gate is always human.

Then:

- If `CLAUDE.md` does not exist: create it with this block.
- If `CLAUDE.md` exists: **do not edit it silently.** Show the block to the user, propose
  where it would be appended, and apply it only on their approval. If a DTDD rules block is
  already present, diff and propose only the delta (or report "already present, nothing to
  do").
